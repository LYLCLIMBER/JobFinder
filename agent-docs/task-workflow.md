# 任务文档工作流

本流程用于创建、执行、交接和关闭可独立验收的任务。简单问答、只读探索、一次性命令和无独立验收价值的小修改不必创建任务文档。

## 1. 判断任务归属

创建新任务前先检查 [`README.md`](README.md) 和现有任务的 `handoff.md`：

- 如果目标属于现有任务的未完成项，继续该任务。
- 如果目标具有独立范围、验收标准和完成状态，创建新任务。
- 如果只是现有任务的非阻塞后续工作，创建新任务并在原 handoff 中建立关联。
- 如果归属或产品目标不明确，先向用户确认，不要同时创建重复任务。

## 2. 分配 Task ID

从索引中选择下一个未使用的 `JF-NNN`。编号一旦分配不得复用，即使任务后来被标记为 `superseded`。

目录使用 `JF-NNN-short-name`：

```text
agent-docs/tasks/JF-003-vision-request-fallback/
```

`short-name` 使用简短、稳定的英文 kebab-case，不在后续状态变化时重命名目录。

## 3. 初始化任务文档

从 [`templates/`](templates/) 创建文档，不直接修改模板来承载具体任务：

```text
JF-NNN-short-name/
├── spec.md
├── handoff.md
└── verification.md
```

复杂任务可以增加 `execution.md`。只有当任务涉及多个阶段、文件、依赖顺序或重要实施约束时才创建它。

所有任务文档必须使用相同的 `task_id` 和任务状态。初始状态通常为 `draft`。

## 4. 编写 Spec

`spec.md` 记录目标行为，不记录当前实施进度。至少明确：

- 目标和背景。
- 范围与不在范围。
- 安全边界和外部依赖。
- 相关代码位置。
- 未决问题。
- 可独立验证的验收标准。

验收项在任务内使用连续的 `AC-NNN`，每项只表达一个主要可观察结果：

```markdown
- `AC-001`：多模态调用失败后重试一次纯文本请求。
- `AC-002`：两次请求都失败时返回结构化失败结果。
```

不要把实施步骤写成验收结果，也不要使用“尽量”“合理”等无法明确判定的条件。

## 5. 初始化 Handoff 和 Verification

`handoff.md` 是后续会话恢复当前状态的唯一入口。创建时应写明：

- 当前状态和是否已开始实施。
- 已知问题、阻塞和待确认事项。
- 下一 agent 可以直接执行的第一步。
- 不应重复的尝试或禁止事项。

`verification.md` 必须列出 spec 中的全部验收项。尚未验证的结果统一写为 `Not run`，不得预先写成 `Passed`。

如果需求或验收标准仍有未决问题，保持 `draft`。目标、范围和验收标准足以实施后，才能转为 `ready`。

## 6. 登记任务

将任务加入 [`README.md`](README.md) 的任务表，链接到该任务的全部已有文档。索引状态必须与 `handoff.md` 一致，但 handoff 仍是当前状态的事实来源。

创建完成后检查：

- Task ID 和目录名没有重复。
- 各文档的 Task ID、状态和验收项一致。
- verification 覆盖 spec 的全部验收项。
- handoff 包含明确下一步。
- 所有相对链接有效。
- 文档没有包含密钥或其他敏感值。

## 7. 开始和执行任务

开始修改代码或实施方案时，将 handoff 和索引状态改为 `in_progress`。工作期间：

- 只处理 spec 定义的范围。
- 代码行为与规范冲突时，在 handoff 登记，不静默宣称已满足规范。
- 新发现的阻塞问题写入 handoff；非阻塞且可独立验收的问题另建任务。
- 有阶段性结果时更新 handoff，不必为每个微小操作更新文档。
- `execution.md` 只记录实施顺序和约束，不承担当前状态记录。

## 8. 验证和交接

实现完成后逐项验证 `AC-NNN`，在 verification 中记录：

- 实际命令和原始结果。
- 验证日期及可用的 revision 或工作区信息。
- 每个验收项的 `Passed`、`Failed`、`Partial`、`Not run` 或 `Not applicable`。
- 测试、代码位置、日志或其他持久证据。
- 未执行项及原因。
- 残余风险。

随后更新 handoff 的已完成、未完成、修改文件、验证结果、下一步和需用户确认事项，并同步索引状态。聊天回复不能替代持久交接记录。

## 9. 状态转换

正常状态流为：

```text
draft → ready → in_progress → review → done
```

其他状态规则：

- 无法继续时使用 `blocked`，并记录解除阻塞所需条件。
- 被新任务替代时使用 `superseded`，并链接替代任务。
- 需求变化后可以从 `review` 或 `in_progress` 返回 `draft`/`ready`，但必须记录原因。
- 只有必需验收项均有通过证据、没有阻塞且文档与实现一致时才能使用 `done`。

## 10. 文档变更检查

至少执行：

```bash
git diff --check
```

并手工检查 Markdown 相对链接、Task ID、状态、验收项映射和旧路径引用。涉及产品代码时，继续执行 [`../AGENTS.md`](../AGENTS.md) 规定的相关测试和静态检查。
