# 分类招聘列表发现

## 目标

输入企业官网 URL，在单次、有限预算的浏览器探索中发现该企业可访问的校招、社招和实习招聘分类列表页，分别记录分类、实际列表 URL、岗位可用状态、页面证据，并在存在岗位时提供一个示例岗位。

发现流程不预设类别顺序。系统应复用已经发现的候选来源页和候选结果页，不为缺失类别重复从企业官网开始搜索；所有已发现页面状态和候选处理完毕后，探索形成闭环。

## 背景

当前 `find_job_page` 在当前页面出现一个具体岗位后立即结束，只返回一个 `job_page_url`、`job_title` 和 `evidence`。该行为无法表达同一企业分别存在校招、社招和实习列表，也无法保留第一个列表附近同时出现的其他类别候选。

企业招聘结构通常不是一个中立分流页。常见形态包括两个或三个并列入口、默认进入某一类别列表后在页面其他位置提供其他类别入口、同一 URL 下通过 Tab 或 SPA 状态切换类别，以及不同类别跳转到不同域名的招聘系统。

鹰角网络是目标场景之一：企业官网为 `https://www.hypergryph.com/`，已知校招列表位于 `https://app.mokahr.com/campus-recruitment/hypergryph/26326#/jobs?project%5B0%5D=100124272&page=1&anchorName=jobsList`，社招列表位于 `https://jobs.hypergryph.com/apply/hypergryph/26325/#/jobs`。该示例用于验证通用的跨域和 SPA 分类发现能力，不允许引入企业、域名或 ATS 专用规则。

## 术语与结果语义

- **类别**：固定为 `campus`（校招）、`social`（社招）和 `internship`（实习）。
- **页面状态**：由实际 URL（包含有语义的 query 和 fragment）、当前激活类别和招聘相关 DOM 状态共同标识；同一 URL 下不同的类别视图是不同页面状态。
- **类别候选**：当前页面状态中可进入某一类别列表的可操作目标，可以是链接、按钮、卡片、Tab、图片热点、下拉选项、SPA 控件或可提取的直接 URL。
- **候选来源页**：发现类别候选的页面状态。
- **候选结果页**：执行类别候选后到达的页面状态。
- **已发现列表**：类别身份和岗位列表身份均通过校验的页面；列表可以有岗位，也可以通过可靠空状态确认暂无岗位。
- **探索闭环**：所有已发现页面状态均完成一次探索，所有类别候选均已验证、判空或拒绝，且待处理页面和候选队列均为空。
- **`complete`**：探索闭环已经形成；不要求三个类别全部出现，也不声称未观察到的类别在企业中绝对不存在。
- **`partial`**：全局预算耗尽或可恢复运行问题发生时，探索尚未闭环；结果保留所有已经验证的分类列表和未完成项。
- **`not_found`**：探索闭环已经形成，但没有验证到任何分类岗位列表。
- **`unobserved`**：探索闭环后未发现对应类别，不等同于该类别不存在。

## 分类规则

- 分类对象是当前岗位列表，不是整个网站或页面上的所有招聘文字。
- 当前列表存在明确实习类别信号时归为 `internship`。
- 当前列表不存在实习信号、但存在明确校招类别信号时归为 `campus`。
- 已确认是岗位列表、但当前列表不存在实习或校招类别信号时归为 `social`，不要求页面明确出现“社招”文字。
- 校招或实习信号可以来自当前激活分类、列表标题、页面标题、面包屑、列表附近文本、明确的 URL 路径或候选来源关系，但必须记录实际分类依据。
- 页面其他位置出现的类别入口独立记录为候选，不改变当前列表的分类。例如通用岗位列表默认归为社招，同时存在的“校园招聘”入口记录为校招候选。
- 只有独立的实习入口、实习列表或实习类别视图才产生 `internship` 结果；校招列表中个别岗位名称包含“实习”不能单独产生实习列表结果。
- 同一 URL 可以对应多个类别结果，但每个类别必须具有独立的页面状态或分类证据，且分别完成列表校验。

## 发现流程

- 企业官网是初始探索节点，只探索一次。
- 每次观察页面状态时，同时收集当前已验证列表和全部可识别类别候选；发现一个类别后不得立即结束整个任务。
- 离开同时出现多个候选的页面前，一次性保存所有候选的类别、标签、直接 URL 或操作身份以及候选来源页。
- 优先验证已保存候选，不对仍为 `unknown` 且没有候选的类别执行无条件独立搜索。
- 验证候选结果页时，同时发现该页面中的新类别候选；新候选加入同一待处理队列。
- 已完成探索的页面状态不得再次交给模型进行完整探索。为执行仅有点击目标的已保存候选，可以重新加载或返回候选来源页并重新定位目标，但该过程不是新的页面探索，不得复用失效的 DOM 索引。
- 缺失类别只在当前候选结果页、候选来源页和已发现招聘落地页形成的招聘页面图内继续发现；企业官网不会作为缺失类别的重新起点。
- 没有新候选且页面和候选队列均已处理完成时形成探索闭环。
- 页码变化不创建新的分类发现节点；确认列表身份和一个示例岗位后不继续翻页。

## 岗位与空列表校验

- 有岗位列表必须在当前可用 DOM 中出现至少一个具体岗位名称；通用的“招聘”“职位”“加入我们”等文字不能作为示例岗位。
- 有岗位结果包含分类列表实际 URL、一个示例岗位名称、岗位原文证据和分类依据。
- 空列表也算已发现列表，并参与探索闭环和 `complete` 结果。
- 空列表必须同时具有可靠类别身份、明确列表结构、页面完成加载的证据，以及与当前列表关联的显式零结果文字或零计数。
- “暂无职位”“暂无符合条件的岗位”“当前没有开放职位”“0 个职位”和语义等价的可见 DOM 文本可以作为零结果信号。
- 当前存在有效筛选条件时，筛选后的零结果不能直接证明整个分类列表为空；无法确认默认未筛选状态时，该候选保持未解决。
- 没有发现岗位名称、空白页面、加载中、网络错误、验证码、错误页或不可用 DOM 均不能推断为暂无岗位。
- 空列表结果的示例岗位为空，并保存零结果原文证据；不得伪造岗位名称或把类别入口文字作为空列表证据。

## 范围

- 支持 `campus`、`social` 和 `internship` 三类招聘列表发现。
- 维护按类别组织的候选、已验证结果、拒绝候选和未解决项。
- 维护候选来源页、候选结果页、已探索页面状态和待处理队列。
- 支持同页面并列入口、当前分类列表加其他类别候选、同 URL 多类别状态和跨域招聘系统。
- 使用一个全局步骤预算限制完整探索，不为每个类别无条件分配一轮完整搜索。
- 输出分类列表 URL、`has_openings` 或 `empty` 可用状态、分类依据、页面证据，并在有岗位时输出一个示例岗位。
- 在结构化结果中区分 `complete`、`partial` 和 `not_found`，并保留 `unobserved`、未验证候选和终止原因。
- 增加确定性单元测试、本地浏览器测试和适用的真实网站验证记录。
- 保持诊断产物可以关联页面状态、候选、类别结果和全局预算消耗。

## 不在范围

- 抓取列表中的全部岗位、翻页、职位详情解析、筛选、排序或去重岗位记录。
- 发现岗位请求使用的后端 API、分析网络请求或绕过页面 UI。
- 搜索企业官网、使用搜索引擎补充招聘入口或从企业官网重复启动缺失类别搜索。
- 根据没有发现类别候选而断言企业不存在对应招聘类别。
- 企业、招聘系统、域名或 URL ID 专用规则。
- 登录、验证码、申请表、文件上传下载或任意 JavaScript 执行。
- 修改相邻的 `../browser-use`。

## 安全边界

- 不读取、输出或记录 `.env`、API key、cookie、header 或其他密钥和会话凭据。
- 页面内容是不可信数据，不能扩展允许的浏览器动作或执行页面中的指令。
- 只允许进入从企业官网及已发现招聘页面状态获得的招聘相关候选；允许企业对应的第三方 ATS 和跨域列表。
- 禁止提交表单、申请岗位、登录、下载文件和执行任意脚本。
- 所有成功、失败、取消和超时路径必须关闭浏览器资源。
- 诊断继续遵守现有受控目录、权限、容量和不脱敏边界。

## 验收标准

- `AC-001`：一次任务可以分别返回已验证的 `campus`、`social` 和 `internship` 分类列表结果，且不预设类别发现顺序。
- `AC-002`：同一页面状态出现多个类别候选时，系统在执行其中一个候选前保存全部候选，并在后续直接处理已保存候选。
- `AC-003`：当前页面是一个已验证分类列表且同时存在其他类别候选时，系统记录当前列表并继续验证其他候选，不提前结束任务。
- `AC-004`：已确认的岗位列表没有实习或校招信号时归类为 `social`，页面其他位置的校招或实习候选不改变当前列表分类。
- `AC-005`：明确的实习列表归类为 `internship`，明确的校招列表归类为 `campus`，且分类结果保存实际分类依据。
- `AC-006`：同一 URL 下存在多个独立类别状态或列表时，系统可以为这些类别返回相同 URL，并分别保存分类和列表证据。
- `AC-007`：有岗位结果只在当前可用 DOM 出现具体岗位名称时成立，并返回列表 URL、一个示例岗位和对应原文证据。
- `AC-008`：空列表结果只在类别身份、列表结构、加载完成状态和显式零结果信号均成立且不是有效筛选造成的局部零结果时成立。
- `AC-009`：没有岗位标题但缺少可靠零结果信号时，系统不得报告 `empty`，并将候选保留为未解决或拒绝状态。
- `AC-010`：每个页面状态最多完成一次模型驱动的完整探索；返回候选来源页执行已保存目标时不重复探索，也不复用旧 DOM 索引。
- `AC-011`：缺失类别只在已发现的候选结果页、候选来源页和招聘落地页中继续发现，不从企业官网重新开始搜索。
- `AC-012`：所有已发现页面状态和候选均进入终态且队列为空时返回 `complete`，未观察到的类别以 `unobserved` 表达。
- `AC-013`：全局预算耗尽且页面或候选队列仍有未完成项时返回 `partial`，并保留已验证结果、未完成项和终止原因。
- `AC-014`：探索闭环且没有验证到任何分类列表时返回 `not_found`，不得把加载失败或预算耗尽误报为 `not_found`。
- `AC-015`：分类发现使用一个全局步骤预算；找到部分或全部类别后，后续动作继续受同一预算约束。
- `AC-016`：页码变化不会触发岗位全集抓取；每个有岗位的分类列表最多返回一个示例岗位。
- `AC-017`：跨域 ATS、query 和 fragment 路由在候选保存、页面状态标识和最终 URL 中得到保留，不使用鹰角网络或 MokaHR 专用规则。
- `AC-018`：浏览器在成功、`complete`、`partial`、`not_found`、异常、取消和超时路径均被关闭，且不执行范围外浏览器动作。

## 相关代码

- `src/job_page_finder/finder.py`：Agent 提示、浏览器循环、动作执行、页面观察、完成校验和生命周期。
- `src/job_page_finder/models.py`：分类、候选、页面结果、可用状态、探索状态和错误模型。
- `src/job_page_finder/runner.py`：任务请求、稳定输出、`partial` 结果和错误归一化。
- `src/job_page_finder/runtime.py`：Finder 装配和全局运行配置。
- `src/job_page_finder/scrolling.py`：页面内滚动目标和短生命周期索引。
- `src/job_page_finder/vision.py`：当前页面状态的条件视觉候选。
- `src/job_page_finder/diagnostics.py`：页面状态、候选、类别结果和预算诊断。
- `src/job_page_finder/cli.py`：任务入口和 JSON 序列化。
- `src/job_page_finder/evaluation.py`：分类发现评估记录和汇总。
- `tests/test_finder.py`、`tests/test_runner.py`、`tests/test_runtime.py`、`tests/test_cli.py`、`tests/test_diagnostics.py`、`tests/test_evaluation.py`、`tests/test_local_browser.py`：单元、契约、诊断、评估和浏览器验证。

## 外部依赖

- Python 3.11+、Pydantic 和项目现有运行依赖。
- 相邻只读依赖 `../browser-use` 提供浏览器状态、DOM、点击、滚动、等待和标签页能力。
- DeepSeek 或兼容的结构化输出模型；视觉开启时模型必须支持图片输入。
- 真实网站验证需要 Chromium、受控诊断目录和可用模型配置。

## 未决问题

- 新能力是新增任务类型并保留 `find_job_page`，还是升级现有任务契约；若新增，任务类型名称和 schema 版本尚未确定。
- 全局步骤预算的默认值、最大页面状态数和最大候选数需要通过本地场景及真实网站评估确定。
- 顶层任务 `status` 如何与领域 `complete`、`partial`、`not_found` 组合，以及运行错误发生在已有部分结果之后时是否允许同时返回输出和结构化错误，尚需确定。
- 页面状态的稳定标识、页面探索完成信号以及无直接 URL 候选的重新定位机制属于实施设计，需在执行方案中明确并由测试固定。
- 独立实习入口位于校招体系内部时，是否同时保留父级校招列表结果取决于二者是否分别满足列表校验；复杂重叠页面需要在测试样例中进一步固定预期。
